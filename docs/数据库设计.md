# 数据库设计

Knodo 的全部业务数据存在一个 SQLite 文件里，由 `better-sqlite3` 同步访问。
本文是数据模型、迁移、全文索引与备份格式的权威说明。

> 相关文档：[开发指南](开发指南.md) · [功能详解 · 效率工具与数据](功能详解-效率工具.md)

---

## 一、文件与约定

- 数据库文件：`<数据目录>/todo.db`（Windows 默认 `%APPDATA%/todo-desktop/todo.db`；
  便携版在 exe 同级 `data/`；也可在「File → 存储位置」改成任意目录）。
- 日志模式：**WAL**（`journal_mode = WAL`），启动时做一次写探测，只读环境会提前报错。
- 时间字段约定：
  - `plan_start` / `plan_end` 存 `YYYY-MM-DD`（仅年月日）；
  - `reminder_at` / `completed_at` / `created_at` / `updated_at` 存 **UTC ISO 8601**。

---

## 二、任务域

### groups — 任务分组

| 字段 | 类型 | 说明 |
|---|---|---|
| id | INTEGER PK | 自增主键 |
| name | TEXT | 分组名称 |
| color | TEXT | 分组颜色（hex） |
| sort_order | INTEGER | 排序（同级内递增） |
| parent_id | INTEGER | 上级分组（自引用，NULL = 顶级；v5 起支持多级） |
| created_at / updated_at | TEXT | 时间戳 |

> 分组名唯一性的作用域是同一 `parent_id`，**刻意不加数据库唯一索引**（旧备份可能同级重名），
> 校验放在 `assertGroupName()`。

### tasks — 任务

| 字段 | 类型 | 说明 |
|---|---|---|
| id | INTEGER PK | 自增主键 |
| group_id | INTEGER FK | 所属分组（`ON DELETE SET NULL`） |
| parent_id | INTEGER | 父任务 id（子任务；删除父任务时由应用层级联删除） |
| title | TEXT | 标题 |
| notes | TEXT | 描述（Markdown） |
| attachments | TEXT | 附件元数据 JSON（文件本体在 `<数据目录>/attachments/task-<id>/`，库里只存相对路径） |
| priority | INTEGER | 0 低 / 1 中 / 2 高 / 3 紧急 |
| plan_start | TEXT | 计划开始日期（`YYYY-MM-DD`，可空） |
| plan_end | TEXT | 计划完成日期（`YYYY-MM-DD`，可空） |
| reminder_at | TEXT | 提醒时间（UTC ISO，可空） |
| reminder_fired | INTEGER | 提醒是否已触发 |
| completed | INTEGER | 是否完成 |
| completed_at | TEXT | 实际完成时间（UTC ISO，完成时自动记录） |
| archived | INTEGER | 是否归档 |
| sort_order | INTEGER | 拖拽排序 |
| created_at / updated_at | TEXT | 时间戳 |

索引：`idx_tasks_group`、`idx_tasks_parent`、`idx_tasks_status`、`idx_tasks_plan_start`、
`idx_tasks_plan_end`、`idx_tasks_completed_at`、`idx_tasks_created_at`。

### tags / task_tags — 标签

| 表 | 字段 | 说明 |
|---|---|---|
| tags | `id`、`name` UNIQUE、`color` | 标签定义 |
| task_tags | `task_id` + `tag_id` 复合主键 | 多对多，两侧 `ON DELETE CASCADE` |

### settings — 键值设置

| 字段 | 类型 | 说明 |
|---|---|---|
| key | TEXT PK | 键 |
| value | TEXT | 值（API Key 为加密后内容） |

常见键：`ai.baseUrl` / `ai.model` / `ai.apiKey` / `ai.asrBaseUrl` / `ai.asrModel` / `ai.asrKey` /
`theme` / `ui.detailWidth` / `ui.sidebarWidth` / `ui.tagFilter` / `ui.todayDone` / `ui.collapsedGroups` /
`tool.salary` / `tool.<key>` / `app.autoStart`。

> `ui.todayDone` 为 `{day, ids}` JSON，记录「今天」里刚完成的任务（跨天自然作废）。

## 三、AI 域

### reports — AI 报告历史（v7）

| 字段 | 说明 |
|---|---|
| id | 自增主键 |
| title | 报告标题（如「周报 2026-10-26 ~ 2026-11-01」） |
| type | `day` / `week` / `month` / `custom` |
| range_start / range_end | 统计区间（`YYYY-MM-DD`） |
| group_ids | 筛选的分组 id JSON 数组（空数组 = 全部） |
| group_label | 分组文案（回看时知道当时筛了什么） |
| extra_prompt | 用户追加的自定义要求 |
| content | 报告正文（Markdown，编辑后自动回写） |
| degraded | 1 = 本地模板报告（未配置 Key / AI 失败） |

### ai_searches — AI 检索历史（v7）

| 字段 | 说明 |
|---|---|
| keyword | 检索关键词 |
| summary | AI 总结（未配置 Key 时为空） |
| task_count | 命中任务数 |
| tasks | 命中任务快照 JSON（回看时无需重新检索） |
| degraded | 1 = AI 总结失败已降级 |

### kb_qa — 知识库问答历史（v12 / v13 补 `scope`）

| 字段 | 说明 |
|---|---|
| question / answer | 提问与回答 |
| hits | 引用片段快照 JSON（content 已截断，避免历史表被大片段撑爆） |
| hit_count | 命中片段数 |
| degraded | 1 = 未走 AI，仅关键词召回 |
| reason | 降级 / 未命中的原因 |
| scope | 当时的检索范围（笔记目录），空串 = 全部笔记 |

## 四、会议域

### meetings — 会议记录（v6）

| 字段 | 说明 |
|---|---|
| title | 会议名称 |
| source_label | 采集说明（「麦克风 + 系统声」/ 窗口名 / 外部导入） |
| mode | `audio` 仅音频 / `screen` 画面 + 音频 |
| started_at | 会议开始时间（UTC ISO） |
| duration_ms | 录制时长（毫秒） |
| media_paths | 分片文件路径 JSON（**绝对路径**，不随数据目录迁移） |
| transcript | 语音转写全文 |
| summary | AI 生成的纪要（Markdown） |
| todos | 提取出的待办 JSON（title / assignee / due / priority / detail） |
| status | `recorded` → `transcribed` → `summarized` |

## 五、笔记与知识库

### note_folders / notes / note_tags / note_tag_map（v9）

| 表 | 关键字段 | 说明 |
|---|---|---|
| note_folders | `parent_id`（自引用）、`color`、`sort_order` | 笔记目录，与分组同构，无限层级 |
| notes | `folder_id`、`title`、`content_md`、`excerpt`、`pinned`、`archived`、`deleted_at`、`word_count`、`content_hash`、`source`、`source_ref`、**`attachments`**（v11） | **正文是唯一权威来源**，摘要 / 字数 / 哈希都是派生；`deleted_at` 非空 = 回收站 |
| note_tags / note_tag_map | `name` UNIQUE / 多对多 | 与任务 `tags` 分开，避免互相污染筛选 |
| notes_fts | FTS5 external content（trigram） | 全文检索，正文不重复存储 |

> `source` 取值 `manual | meeting | ai | import`，`source_ref` 记录来源（例如会议 id）。

### task_notes — 任务 ↔ 笔记（v9）

| 字段 | 说明 |
|---|---|
| task_id | 任务（`ON DELETE CASCADE`：删任务即摘引用） |
| note_id | 笔记（软删除时**保留**关联，恢复后自动复原） |
| created_at | 关联时间 |

### knowledge_bases / kb_documents / kb_chunks / kb_vectors（v10）

| 表 | 说明 |
|---|---|
| knowledge_bases | 知识库注册表；内置「笔记知识库」固定 `id = 1`、`type = 'notes'` |
| kb_documents | 文档；笔记对应 `source_key = 'note:<笔记id>'`，含 `content_hash` 用于增量判定 |
| kb_chunks | 分块（按 Markdown 标题切分，带 `heading_path`），配 `kb_chunks_fts` 供召回 |
| kb_vectors | 向量预留（当前不写入：检索走「查询改写 + 多路召回 + RRF + AI 重排」） |

## 六、全文索引（FTS5）

统一模式：**external content + `tokenize='trigram'` + 触发器同步**。

- external content 表不重复存正文，只存倒排索引，空间省一半；正文更新由触发器推给索引。
- trigram 让中文无需外部分词器即可命中子串，但要求查询词 **≥ 3 个字符**；
  不足 3 字时由 `searchNotes()` 回退到 `LIKE`。
- **不要**在 external content 表上用 `snippet()` / `highlight()` —— 会直接报错，整条 bm25 查询全废；
  片段一律在应用层截取（`highlightOf()`）。

## 七、附件与自定义协议（v11）

笔记图片与任务附件共用 `main/attachments.js`，只是宿主目录不同（`task-<id>` / `note-<id>`）：

- 文件：`<数据目录>/attachments/<kind>-<宿主id>/<附件id>_<文件名>`
- 库里：`tasks.attachments` / `notes.attachments` **只存元数据 JSON（含相对路径）**
- 正文引用：`![](todo-media:///note-<id>/<附件id>_<文件名>)`，由主进程注册的 `todo-media://`
  协议映射回本地文件；只解析 `attachments` 目录内的路径，越界拒绝（`ERR_FILE_NOT_FOUND` / `-6`）

> 用自定义协议而不是 `file://`：`file://` 在渲染层会被 CSP 与路径转义搞出各种边界情况，
> `todo-media://` 只暴露附件目录一个入口，越界直接拒绝。CSP 已包含 `todo-media:`。

## 八、迁移

迁移是 `MIGRATIONS` 数组，按顺序执行、幂等（先查 `PRAGMA table_info` 再 `ALTER`），
版本号取 `PRAGMA user_version`。

| 版本 | 内容 |
|---|---|
| v1 | 初始建表 |
| v2 | 计划日期（`due_at` → `plan_end`，新增 `plan_start`） |
| v3 | 子任务（`tasks.parent_id`） |
| v4 | 任务附件列 |
| v5 | 分组层级（`groups.parent_id`） |
| v6 | 会议录制与纪要 |
| v7 | AI 报告 / 检索历史 |
| v8 | `tasks.created_at` 兜底补列 + 回填 |
| v9 | 笔记模块（目录 / 笔记 / 标签 / 关联 + FTS） |
| v10 | 知识库（文档 / 分块 / 向量预留） |
| v11 | 笔记附件（图片）列 |
| v12 | 知识库问答历史 `kb_qa` |
| v13 | `kb_qa` 补检索范围列 `scope` |

## 九、备份文件格式

一条主链路 + 一份数据格式：

- **完整备份包**（`main/backup.js` → `.zip`）：`manifest.json` + `db.json` + `attachments/` + `recordings/`。
  `db.json` 就是下面 `exportData()` 产出的结构；附件与录音按原目录层级以相对路径打包，
  自检信息（各表条数、附件 / 录音数量、导出时已丢失的文件清单）在 `manifest.json`。
- **自动快照**（`main/backup.js` → `<数据目录>/backups/knodo-YYYYMMDD.db`）：
  SQLite 在线备份接口产出的一致性快照，只保数据库，不含附件与录音文件。

`db.json` 结构（`main/db.js` 的 `exportData()` 产出，`importData()` 消费）：

```json
{
  "app": "todo-desktop",
  "schemaVersion": 12,
  "exportedAt": "2026-11-01T01:20:00.000Z",
  "groups": [], "tags": [], "tasks": [], "task_tags": [],
  "meetings": [], "reports": [], "ai_searches": [], "kb_qa": [],
  "note_folders": [], "notes": [], "note_tags": [], "note_tag_map": [],
  "task_notes": [], "knowledge_bases": [], "settings": []
}
```

规则：

- **不含** AI / 语音 Key（`settings` 里 `ai.apiKey%` 被排除）。
- **不含**派生数据：知识库分块 / 向量 / 全文索引，导入后由笔记正文自动重建。
- `meetings.media_paths` / `todos` 导出时**规范化为数组**（旧版是 JSON 文本，导入时会被当成
  非数组清成 `[]`，录音路径整段丢失）；导入侧仍兼容字符串形态。
- 录音文件在完整备份包里存的是 `recordings/` 下的相对路径，导入时按当前机器的录音目录重写
  `media_paths` 的绝对路径。
- 导入是**覆盖式**：先清空现有分组 / 标签 / 任务 / 会议 / 报告 / 检索 / 问答 / 笔记关联与笔记，
  再写入；本地 `settings`（主题、AI 配置）保留不被覆盖。
- 导入兼容旧版 `due_at` 字段（自动映射为计划完成日期）；`schemaVersion ≥ 7` 的备份才被接受。
