# 工时记薪（时间价值）· 实现方案

> 状态：**P0 已落地（v2.8.0，2026-11-16）**
> 前置：工时插件 v2.6.0 已上线（`worklog_entries` 表、区间聚合、CSV 导出齐备）
> 数据库：新增 **v19 `pay_rates`**，`worklog_entries` 一个字段都不动
> 已定决策：**时薪内核** · **只给自己看（估算，不做工资条）**

---

## 一、定位与边界

**这个功能回答「我这个月的时间值多少钱 / 花在了哪」，不回答「我该拿多少工资」。**

一旦出现「应发 / 实发 / 五险一金 / 个税」，就等于承诺了准确性。而单机应用拿不到考勤、绩效、补贴、地区社保基数——算出来必然是错的，用户还会当真。所以品类定名 **「时间价值」**，界面上一律用「估算」，不出现「薪酬」二字。

### 做什么

- 按时薪把已完成的工时折算成金额
- 按区间（本周 / 本月 / 自定义）汇总，按任务 / 分组拆分
- 金额可逐级回溯：总额 → 任务 → 记录 → 原始工时
- 时薪按生效日期管理，改价不篡改历史

### 不做什么（本期明确排除）

| 不做 | 原因 |
|---|---|
| 工资条（应发/实发/个税/社保） | 数据拿不到，算必错，责任不该背 |
| 加班费法定认定 | 调休、综合工时制、审批流程都不在本地数据里 |
| 团队 / 多人的费率核算 | 单机应用，没有协作数据 |
| 多币种换算 | 字段留 `currency`，UI 不做 |
| 实时「计时器旁边跳钱」 | 会造成"已经在赚钱"的错觉，只在已完成记录上算 |

## 三、计薪模型与口径（本文核心）

### 3.1 公式

```
单条金额（分） = duration_sec × rate_cents ÷ 3600      —— 四舍五入到分
区间总额（分） = Σ 单条金额                             —— 不再二次舍入
```

**为什么汇总用「逐条舍入后相加」而不是「先加后舍」**：数学上后者更精确，但用户核账时的动作是「把明细加一遍」，两者差 1 分他就会认为算错了。**账要能加得上，比多一位精度重要。** 这个取舍写进代码注释，避免后人"优化"掉。

### 3.2 整数分运算（禁浮点）

金额一律以**分**为单位存整数。SQL 里也不走浮点：

```sql
-- 四舍五入到分，纯整数运算（+1800 是 3600 的一半）
CAST((duration_sec * rate_cents + 1800) / 3600 AS INTEGER)
```

验证：3600 秒 × 8000 分（¥80/h）→ (28800000+1800)/3600 = 8000 分 = ¥80.00 ✓
1 秒 × 8000 分 → (8000+1800)/3600 = 2 分（实际 2.22 分）✓

浮点写法 `duration * rate / 3600.0` 在月级数据上会出现 `799.9999999` 这类尾巴，最终展示出错。

### 3.3 费率取值

给定一条记录，取**记录开始日期**（本地日期）之前最近的一条费率：

```sql
SELECT rate_cents FROM pay_rates
 WHERE effective_from <= date(started_at, 'localtime')
 ORDER BY effective_from DESC LIMIT 1
```

三个必须钉死的细节：

1. **`started_at` 存的是 UTC ISO，取日期必须 `'localtime'`**。少了这个修饰符，晚上 8 点之后的记录会被算到第二天（东八区 +8h 跨日），金额和日期都错。
2. **记录早于所有费率**：回落到最早那条，并在界面上标「按最早费率估算」，不静默按 0 算。
3. **一条费率都没有**：不计算，显示引导「先设置你的时薪」，**绝不显示 ¥0.00**——用户会误以为算出结果了。

### 3.4 归属口径

沿用现有 `dayAttr = 'start'`：按开始时间归属。23:00 干到 01:00 算前一天。理由是与工时视图、日报表保持同一口径；不一致会让"工时对得上、钱对不上"。

### 3.5 不计薪（`billable`）

`worklog_entries.billable` 字段**建表时就埋好了，但 UI 从未使用**。本期把它接上：

- `billable = 0` 的记录金额记 0
- 但价值视图必须显示「已排除 12.5 小时」，点击可查看是哪几条
- 入口：报工明细每行一个「计薪 / 不计薪」小开关（P0 就做，否则这字段永远用不上）

### 3.6 加班倍数（P1，默认关闭）

数据支撑已具备：`holidays-cn.js` 提供 `isCnHoliday` / `isCnWorkday` / `describeDay`，覆盖 2026–2027。

| 日期类型 | 倍数 |
|---|---|
| 法定节假日 | 3.0 |
| 休息日（周末且非补班） | 2.0 |
| 工作日（含调休补班） | 1.5 |

**默认关闭**，因为中国的加班认定远比"日期类型"复杂。开启后界面必须写明：

> 按日期类型估算，不代表符合法定加班认定；实际以你的劳动合同与公司制度为准。

这句话不是免责套话——它决定了用户会不会拿这份数字去和 HR 争论。

## 四、数据设计（v19）

```sql
CREATE TABLE IF NOT EXISTS pay_rates (
  id             INTEGER PRIMARY KEY AUTOINCREMENT,
  rate_cents     INTEGER NOT NULL,          -- 每小时单价，单位：分
  effective_from TEXT    NOT NULL,          -- 生效日 YYYY-MM-DD（本地日期）
  currency       TEXT    NOT NULL DEFAULT 'CNY',
  note           TEXT,                      -- 例如「涨薪后」「A 客户报价」
  created_at     TEXT    NOT NULL
);
CREATE UNIQUE INDEX IF NOT EXISTS idx_pay_rate_from ON pay_rates(effective_from);
```

- **`UNIQUE(effective_from)`**：同一天只允许一条，重复保存走 `ON CONFLICT DO UPDATE`（用户改主意不该产生两条）
- **不加外键、不关联任务**：费率是全局时间序列，与任务无关
- `worklog_entries` **不动**：金额是派生值，实时算，不落库

> 为什么不像任务那样存 `hourly_rate`：费率是"时间维度的属性"，存到任务上是错的，存到记录上会产生大量冗余且改价要批量更新。一张独立的时间序列表是唯一正确解。

### 迁移与导出

- `main/db.js` MIGRATIONS 追加第 19 项 → `require('./worklog/schema').migratePay(d)`（DDL 放插件目录，与 v18 同一约定）
- `exportData.schemaVersion` **15 → 16**，导入导出带上 `pay_rates`
- 备份 / 恢复自动跟随（走现有 `db.json` 全量逻辑）

## 五、界面设计

### 5.1 入口：工时视图内的二级切换

**不加侧栏入口，也不加工具栏 chip**——工具栏在 1082 宽度下已经排到两行，加东西必然挤。

在工时视图标题右侧放一个分段控件（复用日历「月 / 周」的 `.seg` 模式）：

```
工时                                     [ 工时 | 价值 ]
本周 · 分组：全部 ▾
```

切到「价值」后，整页换一套数字，表格结构不变：

| 区域 | 工时视图 | 价值视图 |
|---|---|---|
| 汇总卡 | 总工时 / 任务数 / 平均每日 / 最长一天 | **折算价值 ¥8,420** / 可计费时长 / 已排除时长 / 平均时薪 ¥80/h |
| 表格列 | 任务 / 自身 / 含子任务 / 占比 / 操作 | 任务 / 时长 / **金额** / 占比 / 操作 |
| 柱状图 | 每日工时 | 每日金额（同一份数据换个单位） |

第一张卡「折算价值」点击可打开 **时薪设置**。

### 5.2 时薪设置弹窗

```
┌─ 时薪设置 ─────────────────────────────┐
│  时薪    [ 80.00 ] 元 / 小时            │
│  生效日  [ 2026-03-01 ]                 │
│  备注    [ 涨薪后 ]                     │
│                                        │
│  历史费率                               │
│  2026-04-01   ¥100.00/h   涨薪后        │
│  2026-03-01   ¥ 80.00/h                 │
│  2025-06-01   ¥ 60.00/h   接单起步      │
└────────────────────────────────────────┘
```

- 用现成 `openFormModal`，不新写弹窗
- 输入以「元」为单位，保存时 `Math.round(元 × 100)` 转分；**拒绝 ≤ 0 与非数字**
- 生效日默认今天；填历史日期时提示「会重算该日期之后的记录」
- 历史列表按生效日倒序，可删除（删最后一条会导致无费率，二次确认）

### 5.3 明细回溯

价值视图里点任一任务的金额 → 展开该任务的记录列表，每行：日期 / 起止 / 时长 / 费率 / 金额 / 计薪开关。

**每一分钱都必须能点回原始记录**——这是"只给自己看"也要满足的底线，因为用户对不上账时唯一能做的事就是查明细。

## 八、异常与边界

| 场景 | 处理 |
|---|---|
| 未设置时薪 | 引导态，不算、不显示 ¥0 |
| 时薪填 0 / 负数 / 非数字 | 拒绝保存，提示「时薪必须大于 0」 |
| 记录早于最早费率 | 按最早费率估算 + 角标提示 |
| 记录跨天（23:00–01:00） | 按开始日归属，金额归开始日 |
| 任务已删除 | 金额照算，标题显示「已删除任务」（`group_id` 快照兜底） |
| 记录被删除 / 补录 | 金额实时重算，无需手动刷新 |
| 同一生效日重复保存 | upsert 覆盖，不产生两条 |
| 删除最后一条费率 | 二次确认，删后回到引导态 |
| 区间内无记录 | 「本区间没有可计薪的工时」 |
| 时区 / 夏令时 | 统一 `date(started_at,'localtime')` |

## 九、风险

| 风险 | 概率 | 影响 | 缓解 |
|---|---|---|---|
| 用户把估算当实际工资 | 中 | 信任受损 | 全程用「估算」，不用「薪酬」；价值卡脚注一句话说明 |
| 费率历史缺失导致早期记录被错算 | **中高** | 数字错 | 明确标注「按最早费率估算」+ 设置页鼓励补齐历史 |
| 汇总与明细差 1 分 | 低 | 用户质疑 | 已定「Σ逐条舍入」，保证能加得上 |
| 用户以为计时器会实时跳钱 | 中 | 预期不符 | 只在已完成记录上算；工时不显示金额 |
| 加班倍数被当法律依据 | 中 | 合规观感 | 默认关 + 开启时明确措辞 |
| 月薪用户觉得"这不是我要的" | 中 | 功能闲置 | 文档说明月薪可按 21.75×8 折算后填入，不另做一套模型 |

## 附：一句话总结

这个功能的技术难度很低，**难度全在口径**。四个决定成败的判断是：整数分 + 纯整数四舍五入、费率按生效日存时间序列、汇总用「逐条舍入相加」保证能对账、无费率时显示引导而不是 ¥0。把这四条守住了，剩下的都是界面活。

## 十二、落地记录（v2.8.0 · 2026-11-16）

P0 按方案全量落地，口径四处没有走样，实施中补了三个方案里没写到的细节：

| 文件 | 职责 |
|---|---|
| `main/worklog/schema.js` | v19 `pay_rates`（`UNIQUE(effective_from)`），随迁移一次性建表 |
| `main/worklog/store.js` | `listRates / upsertRate / deleteRate / setEntryBillable / payRows` —— **金额的唯一出口** |
| `main/worklog/export.js` | 备份带 `pay_rates`；CSV 追加金额列 |
| `renderer/js/worklog/pay.js` | `money()` 分→¥ 的唯一格式化出口 + 费率弹窗（自绘 DOM，复用 modal 的 class） |
| `renderer/js/worklog/view.js` | 工具栏 `mode=time|value`、价值四卡、按任务金额表（树 + 逐级上卷）、明细回溯与计薪开关 |

三个补充判断：

1. **费率弹窗没用 `openFormModal`**：它的 hint 是转义后的纯文本，做不出「历史费率倒序列表 + 逐行删除 + 删最后一条二次确认 + 点击回填修改」，于是写了专用 DOM 但完整复用 modal 的 class —— 视觉与系统弹窗一致，行为也能承受。
2. **价值视图的树直接复用工时视图的 `aggregate()` 结果**：金额挂到同一棵树上再后序上卷，父行金额 = 自身 + 全部后代。两条视图共用一棵树，才不会出现「工时对得上、钱对不上」。
3. **`billable` 开关放在明细行**：P0 就做，否则这个 v18 就埋好的字段永远用不上；关掉后金额归零、时长保留、卡片显示「已排除」，点卡片能看是哪几条。

验收：`npm run test:pay`（22 项纯内核，含 1 秒 × ¥80 = ¥0.02 无浮点尾巴、跨天归开始日、导入导出前后费率一致）+
`npm run verify:pay`（52 项端到端）。P1（加班倍数 / 每日金额图）与 P2（目标收入 / 任务单价）仍未做。
