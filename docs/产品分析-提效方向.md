# Knodo 产品能力分析与提效方向

> 版本 v1.0 · 2026-11-01 · 基于仓库代码、README 与 docs/ 功能文档的**架构级**分析
> **数据说明**：本文不含真实用户行为数据。所有「预期收益」为逻辑推演，非实测结论；优先级排序依据「链路关键度 × 价值 ÷ 成本」，**不采用 RICE** —— 该项目无用户基数可实测 Reach，强行打分属于伪精确。

---

## 一、当前能力盘点

### 1.1 能力矩阵

| 域 | 已有能力 | 成熟度 |
|---|---|---|
| **任务** | 5 视图（今天/即将到期/全部/已完成/归档）、多级分组无限层、子任务（状态向上递归同步）、4 档优先级、标签多对多、计划时间范围（日粒度）、提醒（分钟级）、4 种排序、时间/关键词/标签三重筛选、详情抽屉、统计（口径切换 + 数字下钻 + 趋势） | 高 |
| **笔记** | Markdown 三态编辑器（编辑/分栏/预览）、代码高亮、Mermaid、粘贴图片、无限层级目录、标签、FTS5 中文全文、回收站、`.md` 导入、附件 | 高 |
| **关联** | 任务 ↔ 笔记多对多（`task_notes`），双向可见引用关系 | 中 |
| **会议** | 麦克风 + 系统声（WASAPI 回环，免虚拟声卡）、5/10/15/30 分钟自动切片、ASR 转写、AI 四段纪要（议题/决议/待办/风险）、行动项勾选批量入任务库 | 高 |
| **AI** | 报告（日/周/月/自定义区间，Word 版式，导出 docx/md，无 Key 降级本地模板）、检索（精确→字面→联想→语义重排 + 命中路径回溯）、知识库 RAG 问答（笔记自动切块 + 标题层级）、文本润色 | 中高 |
| **工具** | 代码格式化、文本对比、JSON 查看、实时薪资（非模态浮窗）；任务导出 CSV、笔记打包 md | 中 |
| **系统** | 本地 SQLite（WAL）、附件与 `todo-media://` 协议、完整备份包（`.zip`，含附件与录音）+ 每日自动快照、存储位置可切换、托盘常驻、提醒轮询（30s）、开机自启、深浅色 | 高 |
| **降级** | 无 Key 全链路可用（报告降级模板、检索降级召回、问答降级关键词） | 高（**这是被低估的资产**） |

### 1.2 架构扩展点（决定新增功能的成本）

| 要加的东西 | 改动处 | 成本 |
|---|---|---|
| 新业务实体 | `db.js` 追加迁移 → `ipc.js` 一组 channel → `preload` 命名空间 → `renderer` 新模块 | 中（4 处，但链路成熟、无构建步骤） |
| 新 AI 能力 | 复用 `main/ai.js::callLLM` 统一入口（改 baseURL/model 只需一处） | **低** |
| 真·全局热键 | `globalShortcut` —— **当前完全空缺** | 低（从 0 到 1，但需新窗口） |
| 后台定时任务 | 新建模块 + `main.js` 启动流程挂载（当前仅 `reminders.js` 一个 30s 轮询） | 低 |
| 流式输出 | `ai.js` 改 stream + IPC 事件推送 + `preload` 事件白名单 | 中 |

## 二、痛点识别

按「**捕获 → 组织 → 沉淀 → 产出 → 维护**」链路排列，标注证据来源。

### 2.1 捕获环节（最薄弱）

| # | 痛点 | 证据 | 影响 |
|---|---|---|---|
| **P1** | **没有全局快捷键**。在任何应用里想到一件事，必须切到 Knodo 或点托盘菜单才会出现「快速添加任务」。 | 全仓 `globalShortcut` 搜索结果为空；托盘菜单才有快速添加 | 这是「记录型工具」的入口瓶颈。入口一不顺，后面所有沉淀与产出都是空转。**同时它是唯一能在不违背本地优先的前提下，缓解「没有手机版」的手段** |
| **P2** | **捕获时要做分类决策**。新建任务表单顺序为「标题 → 分组 → 计划时间 → 更多」，落笔后立刻要选分组和日期。 | 功能文档 §三 就地编辑流程 | 捕获阶段的认知负担会直接降低记录率。成熟做法是「先收进收集箱，整理时再分类」 |

### 2.2 组织环节

| # | 痛点 | 证据 | 影响 |
|---|---|---|---|
| **P3** | **「今天」视图是平铺的**，20 条任务时用户需自行挑选先做哪个；「智能排序」只看截止日期与优先级，不看逾期时长、不看历史完成节奏。 | 功能文档 §五 排序规则 | 每天开场都要重新做一次排序决策，这是高频重复成本 |
| **P4** | **时间只有日粒度**，无法表达「上午/下午」。 | 计划字段刻意只到天（FAQ 明确） | 这一条**建议不改**（见 §六），但可用「时段偏好」低成本替代 |

### 2.3 沉淀环节

| # | 痛点 | 证据 | 影响 |
|---|---|---|---|
| **P5** | **任务与笔记的关联全靠手动**：搜索 + 多选 + 确认。系统不识别内容相关性。 | 详情抽屉「关联笔记」交互 | 关联成本高 → 关联率低 → 「任务与知识长在一起」这个核心主张实际落地率打折 |
| **P6** | **笔记里的行动项无法变成任务**。笔记中写的「下周跟 X 确认」，只能靠人再记一遍。 | 笔记模块无抽取能力；`meeting.js` 的 `extractTodos` 只服务会议 | 「沉淀」止步于文本，没有变成可执行项 —— 这是定位链条上最大的断点 |

### 2.4 产出环节

| # | 痛点 | 证据 | 影响 |
|---|---|---|---|
| **P7** | **产出物不回流**。周报生成后即终点（导出 Word 结束）；报告里 AI 常给出「下月计划」，用户要手动复制成任务。会议纪要能做到办入库，报告却不能。 | `meeting.js` 有待办入库，`report.js` 无对应能力 | 产出与执行断开，「从记录长出来」只走了一半 |
| **P8** | **AI 全部非流式**：60s 超时、一次性返回。周报通常 1500 字以上，用户面对长时间无反馈的空白区。 | `ai.js` `stream:false` | 感知性能差，长报告场景尤甚 |

### 2.5 维护环节（保命项）

| # | 痛点 | 证据 | 影响 |
|---|---|---|---|
| **P9** | **没有自动备份**。`db.backupTo()` 仅在切换存储目录时调用；误删或数据库损坏 = 数据全损。 | `reminders.js` 是唯一后台任务，无备份定时器 | 对「数据是你的」这一核心承诺，这是最大的兑现缺口。**一次事故就会流失一个用户，且不可挽回**<br>✅ 已修复（v1.9.0）：启动 5min + 每 24h 自动快照，保留 7 日 + 4 周，主库打不开可从快照恢复 |
| **P10** | **统计只回答「多少」，不回答「为什么做不完」**。`plan_end` 与 `completed_at` 都在库里，但没有任何「计划 vs 实际」的偏差分析。 | 统计页仅有数量、分组分布、完成趋势 | 已有数据未被利用，而这是唯一能回答「我为什么总延期」的地方 |

## 三、提效功能清单（按优先级）

> 排序依据：**链路关键度**（不做会导致上下游空转）× **价值** ÷ **成本**。P0 = 不做则核心链路断；P1 = 直接提升既有能力密度；P2 = 明确有价值但可延后。

### P0 — 核心链路补强（本期必做）

#### F1 · 全局快速捕获（Global Quick Capture）

| 项 | 内容 |
|---|---|
| 做什么 | 注册全局热键（建议 `Ctrl+Alt+Space`）→ 弹出无边框置顶小窗 → 输入一句话 → 回车即入**收集箱**，不强制选分组/日期；可选「+ 明天 / + 今晚」快捷后置 |
| 解决问题 | P1、P2 |
| 价值 | 把「想到 → 记下」从「切应用 + 3 次点击」压缩到「一个热键 + 一句话」。这是本地工具最高杠杆的一处改动 |
| 预期收益 | 记录量提升（逻辑推演：摩擦降低必然提高捕获率）；同时**部分补偿没有手机版的场景缺口**（在别的应用里也能随时记） |
| 难度 | 中低。新增 `globalShortcut` 注册 + 一个轻量 BrowserWindow；数据落 `tasks` 的收集箱分组，**无需新表** |
| 所需条件 | ① 定义一个固定「收集箱」分组（或 `group_id = NULL` 作为语义上的收集箱，需确认现有查询是否已支持）；② 极简 NLP：日期短语正则（今天/明天/后天/周X/MM-DD）优先，AI 解析作为可选增强 |
| 风险 | 全局热键被其他软件占用 → 需在设置里可改；置顶小窗抢焦点 → 需 `skipTaskbar + alwaysOnTop + blur 自动隐藏` |

#### F2 · 自动备份与快照轮转

| 项 | 内容 |
|---|---|
| 做什么 | 每天首次启动 + 每 6 小时，将 `todo.db` 快照到 `<dataDir>/backups/todo-YYYYMMDD-HHmm.db`；保留最近 7 份日快照 + 4 份周快照，超限自动清理 |
| 解决问题 | P9 |
| 价值 | 「本地优先」的信用底座。不是提效，是防流失 |
| 预期收益 | 消除单点数据全损风险；也让「数据目录指向 U 盘、拔盘」这类故障有退路 |
| 难度 | **低**。`db.backupTo()` 已实现，只需新建 `main/backup.js` 定时器 + 轮转逻辑 + `main.js` 挂载 |
| 所需条件 | 快照要在 WAL checkpoint 之后执行（或直接用 better-sqlite3 的 backup API，它自带一致性保证）；清理逻辑需避免误删非快照文件 |
| 风险 | 数据目录在移动硬盘且已拔出 → 备份失败要静默跳过，不能弹窗打断 |
| **落地（v1.9.0）** | 已实现，三处与本文设想不同：① 频率取「启动后 5 分钟首备 + 每 24h」，比「每天首次启动 + 每 6 小时」更省磁盘，日粒度任务不需要 6 小时快照；② 快照前 `PRAGMA quick_check`，本轮库已坏则不覆盖历史备份；③ 附带「完整备份包」（`.zip` 含附件与录音）与启动期坏库恢复入口，超出本文范围但同属 P9 |

#### F3 · 计划 vs 实际偏差分析

| 项 | 内容 |
|---|---|
| 做什么 | 统计页新增一块：按时完成率、平均延期天数、延期 Top5 分组、最常被改期的任务（`updated_at` 与 `plan_end` 差异） |
| 解决问题 | P10 |
| 价值 | 把所有待办工具只统计「做了多少」升级为「为什么做不完」，且**零新数据采集** |
| 预期收益 | 统计页从「看数字」变成「找问题」，是笔记/报告之外第三个可回访的理由 |
| 难度 | **低**。纯 SQL 聚合 + 统计页加一个卡片区，无需迁移 |
| 所需条件 | 需先定义口径：按时完成 = `completed_at` 日期 ≤ `plan_end`；无 `plan_end` 的任务不计入分母（口径要写在界面上，否则数字不可信） |
| 风险 | 历史数据缺失 `plan_end` 时口径会失真 → 需显示样本量（如「基于 42 个有截止日期的任务」） |

### P1 — 能力密度提升（下一版本）

#### F4 · 报告 / 纪要 → 任务的双向回流

| 项 | 内容 |
|---|---|
| 做什么 | 在 AI 报告正文中识别列表项，逐条给出「加入任务」勾选框（可指定分组/日期），一键批量建任务；同时把报告的 Markdown 存为笔记并自动关联到生成的任务 |
| 解决问题 | P7 |
| 价值 | 闭合「产出 → 执行」的回路。会议纪要已证明这个交互成立（行动项批量入任务），复用同一套心智成本极低 |
| 预期收益 | 周报从「写完就结束」变成「下个月的起点」，是产品叙事最完整的一环 |
| 难度 | 中低。`meeting.js::extractTodos` 的结构可直接复用；UI 复用会议纪要的勾选列表；需新增「报告 → 任务」的 IPC 通道 |
| 所需条件 | 报告正文的列表解析规则要稳（先按 Markdown 列表解析，不依赖 AI 重新抽取，避免二次调用与不确定输出） |

#### F5 · 笔记 → 行动项抽取

| 项 | 内容 |
|---|---|
| 做什么 | 笔记详情加「提取待办」：AI 扫描正文，输出候选行动项（含建议日期/优先级），勾选后批量入任务，并**自动建立 `task_notes` 关联** |
| 解决问题 | P6、P5（部分） |
| 价值 | 把「沉淀」变成「可执行」，是产品定位的核心增量。且关联自动建立，提升「任务与知识长在一起」的实际落地率 |
| 预期收益 | 笔记从「存档」变为「生产资料的来源」；关联率提升会反过来增强 AI 检索与问答的质量（引用更完整） |
| 难度 | **低**。复用 `ai.callLLM` + 一个结构化 prompt（输出 JSON 数组）；UI 复用会议的待办预览 |
| 所需条件 | 必须可关闭（全局设置 + 单次取消）；抽取结果必须原文可溯源（点候选能跳回笔记对应段落），否则信任成本高于收益 |
| 风险 | 误报污染任务列表 → 默认「只给候选、不直接写入」；无 Key 时回退为「按 Markdown 待办语法 `- [ ]` 提取」，保持降级可用 |

#### F6 · AI 报告 / 检索流式输出

| 项 | 内容 |
|---|---|
| 做什么 | `ai.js` 增加 `stream: true` 分支，通过 IPC 事件逐段推送；报告与检索页改为增量渲染，可中断 |
| 解决问题 | P8 |
| 价值 | 感知性能质变。60s 空白 → 首字 1–2s 出现 |
| 预期收益 | 长报告场景（周报/月报）放弃率下降；也让「可中断」成为可能（当前只能干等超时） |
| 难度 | 中。`ai.js` + IPC 事件通道 + `preload` 事件白名单（已有 9 个 `ui:*` 的现成机制）+ 渲染层增量更新 |
| 所需条件 | 要处理半截 JSON / 半截 Markdown 的渲染容错；取消时需主动 abort 底层请求，避免连接悬挂 |
| 风险 | 事件通道若不走白名单会撕开 preload 的收口约定 → 必须显式登记 |

#### F7 · 「接下来做什么」推荐（Today 聚焦）

| 项 | 内容 |
|---|---|
| 做什么 | 在「今天」视图顶部新增 3 条建议：逾期最久、今天到期且优先级最高、计划今天开始但未动。可直接勾选开始、或一键「推迟到明天」 |
| 解决问题 | P3 |
| 价值 | 把「每天重新排序」这个高频决策自动化 |
| 预期收益 | 「今天」视图从列表升级为工作台；配合 F3 的偏差数据，推荐会随使用变准 |
| 难度 | 中低。本地规则即可（无 Key 可用），可选 AI 重排作为增强 |
| 所需条件 | 规则要可解释（每条建议标注理由，如「逾期 4 天」），否则用户不信任推荐 |
| 风险 | 推荐不准会伤害信任 → 首版只做 3 条强规则，不做「智能排序」这类黑箱 |

### P2 — 明确有价值，本期不做

| # | 功能 | 为什么延后 |
|---|---|---|
| F8 | 任务描述 ⇄ 笔记互转（描述「提升为笔记」、笔记段落「拆成任务」） | 价值明确（消除两套 Markdown 的割裂），但涉及编辑器状态迁移与双向同步，成本高于 F1–F7，且可被 F5 部分覆盖 |
| F9 | 数据目录放进同步盘的一键引导（含冲突检测） | 「多设备」的合规替代方案，但冲突合并语义复杂，建议先只做「检测到同步盘时提示风险」，不做合并 |
| F10 | 笔记编辑与任务描述编辑器统一 | 长期债务，但改动面横跨两个高成熟模块，性价比最低 |

## 四、实现难度与条件评估汇总

| 功能 | 改动面 | 新增数据表 | 依赖外部 | 预估成本 | 主要技术风险 |
|---|---|---|---|---|---|
| F1 全局捕获 | 主进程新窗口 + globalShortcut + IPC + 渲染层新模块 | 否 | 否 | 中 | 热键冲突、焦点抢占、多屏定位 |
| F2 自动备份 | 新模块 `backup.js` + main.js 挂载 | 否 | 否 | 低 | WAL 一致性、目录不可用静默处理 |
| F3 偏差分析 | 统计 SQL + 统计页 UI | 否 | 否 | 低 | 口径定义与样本量披露 |
| F4 报告回流 | IPC 通道 + 报告页 UI + 复用 extractTodos | 否 | 否 | 中低 | Markdown 列表解析的边界（嵌套/编号/引用） |
| F5 笔记抽取 | 复用 callLLM + 笔记页 UI | 否 | 需 AI Key（可降级） | 低 | 误报控制、原文溯源 |
| F6 流式 | ai.js + IPC 事件 + preload 白名单 + 渲染层 | 否 | 否 | 中 | 半截内容渲染、取消时连接回收 |
| F7 Today 推荐 | 查询 + 视图 UI | 否 | 否 | 中低 | 推荐可解释性 |

> **共性结论**：F1–F7 **全部不需要新增数据表**，全部可复用现有 IPC/preload/迁移机制。这意味着本期提效改造的风险主要在 UI 与主进程窗口管理，不在数据层。这是一个可以放心排期的信号。

## 五、建议落地优先级与下一步行动

### 5.1 版本切分建议

**本期（建议命名 v1.9「捕获与保命」）**
```
F2 自动备份   → 先做，半天到一天，纯收益零风险，先消除数据全损隐患
F1 全局捕获   → 本期主线，产品叙事的入口必须打通
F3 偏差分析   → 与 F1 并行，纯查询，不抢资源
```

**下一版（v1.10「闭环」）**
```
F4 报告回流   → 闭合产出→执行
F5 笔记抽取   → 闭合沉淀→执行，且自动建立关联
```

**再后（v1.11「体验」）**
```
F6 流式输出 + F7 Today 推荐
```

### 5.2 下一步行动（按顺序）

1. **确认三个产品口径**（需你拍板，我不能替你决定）：
   - 收集箱是「固定分组」还是「`group_id = NULL`」？（影响 F1 的数据落点与现有查询兼容性）
   - 自动备份默认开启还是首次启动询问？（本地优先产品我建议**默认开启**，且不提供关闭以外的打扰）
   - 偏差分析的分母是否包含无截止日期的任务？（建议不包含，但要在界面写清样本量）
2. **先做 F2**：单点、无 UI、可立刻验证备份可用性（造一份假数据 → 恢复 → 比对）。这是唯一「做了就一定对」的功能。
3. **F1 做技术预研**：`globalShortcut` 在 Electron 中与输入法、全屏应用、多屏切换的兼容性；建议先做一个只有输入框的原型，验证「热键唤起 → 输入 → 入库 → 自动隐藏」这条 4 步链路，再补 NLP 解析。
4. **F3 先定口径再写 SQL**：口径不清的统计比没有统计更坏。
5. **每一项完成后同步更新** `docs/功能详解-*.md` 与 `数据库设计.md`（本期虽无新表，但迁移版本号、设置键需登记）。

### 5.3 建议的验证方式

| 功能 | 验证标准 |
|---|---|
| F2 | 删除 `todo.db` 后能从 backups 恢复到最近快照，且任务数/笔记数一致 |
| F1 | 在记事本、浏览器全屏、IDE 三种前台应用下按热键，均能在 300ms 内唤起；Esc 消失且不抢焦点 |

| F5 | 同一篇笔记连续抽取两次，候选集重合度 ≥70%（稳定性）；无 Key 时按 `- [ ]` 语法降级可用 |

## 六、不建议做的清单（同样重要）

| 不做 | 理由 |
|---|---|
| 番茄钟 / 习惯打卡 / 倒数日 | 进入竞品的主场，且与「记录与产出」定位无关；做了会稀释主链路 |
| 日历视图（年/月/周/日/时间线全家桶） | 计划本身是日粒度，做日历视图等于先改数据模型再改交互，成本极高、收益与定位不符 |
| 团队协作 / 共享清单 | 一旦做协作，界面就开始为「管理别人的进度」服务，与「管我自己的事」直接冲突 |
| 精确到时分的时间块 | 会破坏排序与筛选的简单性（FAQ 已明确这是刻意取舍）。若确有需求，用「上午/下午/晚上」的**时段偏好**替代，不改时间字段语义 |
| 主题商店 / 皮肤系统 | 与提效无关，纯消耗维护成本 |
| 云同步 / 账号体系 | 与「数据是你的」根本冲突。多设备诉求用「数据目录放同步盘 + 导出备份」解决，不引入账号 |

## 七、一句话结论

**当前产品的功能密度已经够用，真正的提效空间不在「再加一个功能模块」，而在两处：**
**① 把「想到」到「记下」的路径压到一个热键（F1）；② 让已有数据自己流向下一步（F2 保命、F4 产出回流、F5 沉淀转执行）。**
这三件事都不需要新数据表，全部落在现有架构的扩展点上。

> 本方案为产品设计参考，具体实施请结合项目实际约束与个人时间投入确认。
